Задание 6. Отфильтруйте ранее выделенные АТД по правилам "Основные рекомендации по отбраковке потенциальных АТД",
укажите, почему вы отказались от тех или иных классов.

===========================================================
Обозначения:
"-" - класс убран и функционал понятно, куда переносить
"?" - класс убран, но не ясно, как реализовывать функционал
"new" - класс добавлен (и удовлетворяет критериям)
"+" - класс удовлетворяет критериям

===========================================================
Основные классы анализа (АТД) в проекте -- только на уровне их названий (на английском) 
и краткое описания в несколько слов (на русском).


- Game - игра в целом (то, что относится ко всей игре: заставка и режимы).
-> Исключено, но не как отбраковка АТД, а потому что этот функционал реализуют классы проектирования.

+ Board - игровое поле (само поле с набором "низкоуровневых" команд "очистить поле", "сдвинуть элементы вниз", "заполнить свободное место",
                        "поменять местами два элемента", "убрать фигуру" и т.д., а также запросами, позволяющими вернуть поле в необходимых форматах).
-> Оставлено (предполагалось наследование Board от АТД TwoDimensionalArray, но сейчас решение всю функциональность 
              обоих АТД сосредоточить в Board, также сюда добавлена вся функциональность из BoardAction и BoardSearch).

- BoardAction - действия (изменения) на поле (заполнение, убирание фигур, 
применение бонусов).
-> Класс убран, функциональность перенесена в АТД Board.

- BoardSearch - поиск на поле (проверка наличия фигур и бонусов, проверка, 
что нет ходов за игрока (что проигрыш игрока)).
-> Класс убран, функциональность перенесена в АТД Board.

- BoardView - отображение поля в разных вариантах (просто поля и поля с дополнительной 
информацией о очках и бонусах).
-> АТД переименован в UserIO, потому что, во-первых, отображаем не только поле и, во-вторых,
будет добавлено в АТД также получение данных от пользователя.

new UserIO - "Пользовательский ввод-вывод" - отображение поля и другой информации и получение команд от пользователя.
-> АТД удовлетворяет критериям.

+ BoardElementTypes - типы элементов (исходные, текущие и текущие для показа бонусной фигуры).
-> АТД удовлетворяет критериям.

+ Shapes - фигуры (шаблоны фигур для удаления и шаблоны ручных и автоматических бонусов).
-> АТД оставлен (это, по сути, константы - льготное наследование). Но добавлен ещё класс (Shape).

new Shape - фигура (одна фигура для поиска на поле или для возврата найденной фигуры).
-> АТД по сути константы (льготное наследование).

new Bonus - бонус (бонус это фигура - Shape и действие - BonusAction).
-> АТД по сути константы (льготное наследование).

+ BonusActions - действия бонусов.
-> АТД оставлен (это льготное наследование) - здесь не сами действия, а их название,
   сами действия в классе Board.

- Bonuses - бонусы, которые игрок набрал, но ещё не использовал.
-> АТД убран, его функционал есть в классе проектирования Context.

- Scores - очки, которые набрал игрок.
-> АТД убран, его функционал есть в классе проектирования Context.

- GamerTurn - ход игрока (выводит подсказку, получает ввод, проверяет его и возвращает).
-> АТД убран, его функционал есть в классе проектирования CommandLoopState.

- GameMechanics - механика игры (знает в каком порядке делать какие действия с полем 
и когда запрашивать ход игрока).
-> АТД убран, его функционал есть в классе проектирования PhaseState и других.

+ TurnHistory - история ходов.
-> АТД удовлетворяет критериям.

===========================================================
Основные классы реализации (АТД) в проекте -- только на уровне их названий (на английском) 
и краткое описания в несколько слов (на русском).


- TwoDimensionalArray - двумерный массив. Он будет основой для доски, потому-что к ней много обращений 
и есть нагруженные операции типа поиск, есть ли ход за игрока. Соответственно, нужна как быстрая реализация,
так и скрытие возможности обращения в обход методов класса.
-> АТД убран, его функционал перенесён в класс анализа Board.

===========================================================
Основные классы проектирования (АТД) в проекте.


Использую следующие паттерны:

I. Паттерн State (Статус). Классы:

+ Context - класс хранит текущую фазу (как композицию), признак завершения, очередь накопленных автоматических бонусов и список ручных бонусов
-> АТД удовлетворяет критериям.

+ Phase - Фазы программы (просто перечень фаз конечного автомата: SHAPES_DELETE_LOOP, AUTOMATIC_BONUSES_LOOP, AWAIT_COMMAND, 
FINISH_STATE, EXIT_STATE).
-> АТД оставлен (это, по сути, константы - льготное наследование).

+ PhaseState - абстрактный класс с одним методом step - один шаг обработки, возвращает следующую фазу программы.
-> АТД удовлетворяет критериям.

+ DeletingShapesLoopState - наследник PhaseState (тот же АТД) - фаза удаления фигур.
+ AutomaticBonusesHandlingLoopState - наследник PhaseState (тот же АТД) - фаза обработки автоматических бонусов.
+ CommandLoopState - наследник PhaseState (тот же АТД) - фаза обработки команд игрока.


II. Паттерн Strategy (Стратегия). Классы:

+ OutputPoint - просто перечисление точек вывода (SHAPES_DELETE_SHOW_FIND_BONUS, SHAPES_DELETE_AFTER_DELETE, 
                                                SHAPES_DELETE_AFTER_SHIFT, SHAPES_DELETE_FINAL, AUTOMATIC_BONUSES_AFTER_USE, 
                                                FINAL_BEFORE_WAITING_COMMAND).
-> АТД оставлен (это, по сути, константы - льготное наследование).

- Report - само событие вывода (содержит точку вывода и прочую информацию для вывода).
-> оставлен, но не как АТД, а как неизменяемая структура данных.

+ OutputPolicy - абстрактный класс - тип вывода (все промежуточные поля или только финальное, также можно сделать вообще без вывода (для тестирования)).
-> АТД удовлетворяет критериям (только запросы, но это ""неизменяемая" внешняя сущность - тип вывода).
+ EachBoardOutputPolicy - наследник OutputPolicy (тот же АТД) - выводить все поля.
+ FinalBoardOutputPolicy - наследник OutputPolicy (тот же АТД) - выводить только финальное поле.
+ NoBoardOutputPolicy - наследник OutputPolicy (тот же АТД) - не выводить никакие поля.

+ Reporter - класс, который помнит текущий тип вывода и содержит методы для переключения типа вывода (также, как и PhaseState, его хранит Context).
-> АТД удовлетворяет критериям.


III. Паттерн Command (Команда). Классы:

+ Command - команда игрока - абстрактный класс.
-> АТД удовлетворяет критериям.
+ ChangeTwoElementsCommand - наследник Command (тот же АТД) - перестановка 2-х соседних элементов.
+ UseBonusCommand - наследник Command (тот же АТД) - использовать бонус.
+ ShowStepHistoryCommand - наследник Command (тот же АТД) - показать историю ходов.
+ QuitCommand - наследник Command (тот же АТД) - завершить игру.
+ RestartCommand - наследник Command (тот же АТД) - перезапустить игру.
+ ChangeToEachBoardOutput - наследник Command (тот же АТД) - переключиться в режим показа каждого поля.
+ ChangeToFinalBoardOutput - наследник Command (тот же АТД) - переключиться в режим показа только финального поля.

IV. Остальное.

+ Engine - класс реализующий основной цикл игры (он "двигает" игру вначале и между командами игрока).
-> АТД удовлетворяет критериям.
